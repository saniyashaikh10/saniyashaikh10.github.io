Case Study 03

AI Business Analyst Assistant

Ask it "why did revenue drop in March?" in plain English. It writes the SQL, pulls the data, and gives you the answer — no analyst required. And when it got confused, I found out why.

Python SQLite LLM API
01

Business Problem

Analysts spend a lot of time answering the same kinds of repetitive business questions — "why did X change," "which category is underperforming." I built a working prototype of a tool that answers these directly: a business user types a question in plain English, and the system writes the SQL, runs it against a real database, and returns a written insight, not just a number.

02

Architecture

1 Plain-English question
→
2 LLM generates SQL
→
3 Query runs on real DB

Built on the same normalized Superstore database from Project 02, using the Groq API (an open-source LLM) for both the SQL generation and insight-writing steps.

03

It works — here's a real example

Question asked in plain English, with zero manual SQL:

"Why might Furniture be underperforming compared to other categories?"

The system automatically generated and ran this:

SELECT p."Category",
       COUNT(DISTINCT o."Order ID") AS "Orders Count",
       SUM(oi."Sales") AS "Total Sales",
       SUM(oi."Profit") AS "Total Profit",
       ROUND(AVG(oi."Discount") * 100, 2) AS "Avg Discount (%)",
       ROUND(AVG(oi."Profit" / NULLIF(oi."Sales", 0)) * 100, 2) AS "Avg Profit Margin (%)"
FROM order_items AS oi
JOIN orders AS o ON oi."Order ID" = o."Order ID"
JOIN products AS p ON oi."Product ID" = p."Product ID"
GROUP BY p."Category"
ORDER BY "Total Sales" DESC;

And returned this written insight:

Furniture has 1,764 orders but generates only $741,999 in sales versus $836,154 for Technology and $719,047 for Office Supplies, despite a higher order volume. Its profit margin is only 3.88% compared to 15.61% for Technology and 13.80% for Office Supplies, and the average discount is 17.39%, the highest of the three categories. The combination of steep discounts and low margin is driving the underperformance.

This matches the independent finding from Project 01's manual analysis — the AI arrived at the same conclusion (discounting is driving Furniture's underperformance) with no prior knowledge of that earlier work.

04

Where it broke — and why that matters more

Testing isn't just about showing what works. I asked a deliberately vague question and it revealed a real limitation:

Vague question

"Which region should we focus on to improve profit?"

West — the AI found the highest-profit region and wrote a confident justification for investing there.

Precise question

"Which region has the lowest profit margin and needs improvement?"

South (7.51% margin) — correctly identifies the actual weakest region.

The takeaway: the AI answered a technically-valid but logically-backwards question fluently and confidently — it didn't know it had misunderstood. This is a real, known limitation of LLM-based tools: they optimize for a plausible-sounding answer, not for catching ambiguity in the question itself. A production version of this tool would need guardrails — clarifying questions, or a human review step — before it could be trusted unsupervised.

05

What I'd do next

  • Add a clarification step: if a question could be interpreted multiple ways, have the AI ask which one before running the query
  • Validate generated SQL before execution (check it only reads data, matches the real schema, and isn't malformed)
  • Wrap this in a simple chat interface instead of a notebook, so a non-technical user could actually use it
